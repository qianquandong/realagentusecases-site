01 · AI 前台 · 线上运行打电话或发短信 (469) 425-4142 · 中英西三语

AI 前台：电话和短信都能接，查档期、完成预约

问题

小店忙着招呼客人时接不到电话、回不了短信；每个预约都要来回确认时间；潜在客户也应该能在销售电话之前，不注册就先试一试这个前台。

交付

OpenAI Realtime 语音线和短信 agent 共用一套 tool（查档期、新建 / 查找 / 改期 / 取消预约），打同一个预约 API（Cloudflare Pages Functions + Supabase Postgres）。每次确认的变更都会给顾客和店主各发一条短信。aimanjack.com 上有公开落地页和自助预约页；同一套短信模式跑在 DFW 一家二手车行的号码上。

边界

只报核准过的价格，其余一律转人工；防双重预订做在数据库里，不只靠 prompt；改期和取消有提前时间限制；不收款；每次写入都发确认短信，漏看的对话也能浮出来。

架构与取舍

Twilio 只当管道：TwiML 把通话交给 WebSocket 桥接，来电号码作为参数带进去，语音和短信走同一个 tool 执行器。预约 API 是唯一写入口，容量检查和 advisory lock 放在 Postgres 函数里，所以模型出错最坏是说错一句话，不会产生错误预约。调试接口可以不打电话逐个跑 tool，每次改 API 都跑一遍冒烟测试。

02 · 运营自动化 · 线上运行运营负责人每周省下约 4 小时

TikTok Shop 直播代运营公司的每周主播排班系统

问题

运营负责人每周在群里收主播和运营的可播时间，在 Lark 表格里一格一格拖出几个直播间的班表，还要每天手写一份每人的计划。班表和大家真实可播时间的冲突，全靠肉眼核对。

交付

主播通过带签名的专属链接提交下周可播时间。Cloudflare Worker（KV + cron）从 Lark 表格读取评分、搭档限制、工时上下限和直播间要求，跑约束求解，把排班草案和明确的缺口清单写回 Lark。Admin 面板能看到谁交了、草案到哪一步。

边界

系统只出草案，审核和发布都由运营负责人完成。单场不少于两小时；没人能顶的时段留空并列进缺口清单，不硬塞。不用任何人的个人 Lark 身份，机器不发消息，密钥只放在 Cloudflare。

架构与取舍

整套跑在 Cloudflare 上（Worker + KV + cron），用 Lark 应用凭证读写，不依赖任何人的电脑。Lark 仍是唯一数据源：提交记录进 Lark Base，草案进 Lark 表格，运营负责人还在她熟悉的地方改。每个提交链接带姓名和周次的 HMAC 签名，过期链接交不了。21 个回归测试覆盖求解器和链接签名，push 即部署，交接文档让下一个维护者不靠我也能跑。

问题
